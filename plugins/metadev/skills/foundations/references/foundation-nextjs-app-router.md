## Route groups

- A folder whose name is wrapped in parentheses, such as `(workspace)`, is a route group. It does not add a URL segment.
- A `layout.tsx` inside a route group wraps every page in that group. This gives several views one shared shell without a shared URL prefix.
- Routes outside the group do not get the group's layout.
- Two routes in different groups that resolve to the same URL path cause an error.

```
app/
  (workspace)/          -- route group, no URL segment
    layout.tsx          -- shared shell for the group
    page.tsx            -- renders at /
    chat/
      page.tsx          -- renders at /chat
    artifacts/
      [id]/
        page.tsx        -- renders at /artifacts/[id]
  login/
    page.tsx            -- renders at /login, outside the shell
```

## Dynamic route parameters

- `params` is a Promise from Next.js 15.0.0 onward. This applies to `page`, `layout`, `default` and route handlers (`route.ts`), and to `generateMetadata`. `searchParams` in `page` became a Promise in the same release.
- `cookies()`, `headers()` and `draftMode()` from `next/headers` became asynchronous in the same change (15.0.0) and have to be awaited.
- Next.js 14 and earlier: `params` and `searchParams` are plain synchronous objects.
- Next.js 15: the async form is the documented one. Synchronous access still works as a temporary compatibility path and logs a warning in development.
- Next.js 16: synchronous access is removed. These values can only be read with `await` (or with React `use()` in a non-async component).
- A client component page cannot be `async`; it reads the Promise with `use(params)` from `react`.
- `npx next typegen` (available from 15.5; types are also generated by `next dev` and `next build`) provides the global type helpers `PageProps<'/route/[id]'>`, `LayoutProps<'/route'>` and `RouteContext<'/route/[id]'>`. They need no import. Writing the type by hand as `Promise<{ id: string }>` remains valid.

Synchronous form (Next.js 14 and earlier only):

```typescript
export default function Page({ params }: { params: { id: string } }) {
  const { id } = params;
}
```

Async form (Next.js 15 and 16):

```typescript
export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
}
```

Async form with the generated helper (Next.js 15.5 and later):

```typescript
export default async function Page(props: PageProps<'/artifacts/[id]'>) {
  const { id } = await props.params;
  const query = await props.searchParams;
}
```

Client component page (Next.js 15 and 16):

```typescript
'use client';
import { use } from 'react';

export default function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = use(params);
}
```

API route handler (Next.js 15 and 16):

```typescript
export async function GET(
  req: Request,
  { params }: { params: Promise<{ id: string }> }
) {
  const { id } = await params;
}
```

## Server and client components

| | Server component | Client component |
| --- | --- | --- |
| How it is declared | Default in the App Router (pages and layouts are server components by default) | `'use client'` at the top of the file, above the imports |
| Data fetching | Can fetch on the server with `await` | Fetches in the browser |
| Client bundle | Its code is not added to the client bundle | Its code is shipped to the browser, together with everything the file imports |
| Hooks (`useState`, `useEffect`, `useContext`) | Not available | Available |
| Event handlers (`onClick`, `onChange`) | Not available | Available |
| Browser APIs (`localStorage`, `navigator`) | Not available | Available in the browser only (in effects and event handlers) |

- A client component is also rendered on the server to produce the initial HTML on a direct visit, and then again in the browser during hydration. Browser APIs do not exist during that server render.
- `'use client'` marks a boundary: it is needed only on the file that enters a client subtree, not on every file below it.
- Third-party libraries that use hooks only work inside client components. A library component whose module has no `'use client'` directive raises an error when used directly in a server component; it works when imported from a file that has the directive.
- React Context is not supported in server components.
- Props passed from a server component to a client component have to be serializable. A plain function such as an event handler cannot be passed.
- A server component can render a client component and pass it fetched data as props:

```typescript
// app/(workspace)/page.tsx (server component)
export default async function DashboardPage() {
  const items = await fetchItems();          // server-side fetch
  return <ItemsList items={items} />;        // client component
}

// components/dashboard/ItemsList.tsx (client component)
'use client';
export function ItemsList({ items }) {
  const [expanded, setExpanded] = useState(false);
  // ...
}
```

- The documented way to share a React Context provider is a separate client component that accepts `children`, rendered from a layout that stays a server component.
- A layout can be a client component (`'use client'` in `layout.tsx`) and can then hold a React Context provider for the pages under it (unverified: the documentation states that a page can be a client component and shows only the separate-provider pattern for layouts; it does not state this for `layout.tsx`).

## Code splitting

- `await import('@/lib/module')` inside a function in a client component loads that module as a separate chunk at the moment the function runs. The chunk is not part of the initial bundle and appears in the browser's network tab only when it is requested.

```typescript
const handleAction = async () => {
  const { heavyFunction } = await import('@/lib/heavy-module');
  await heavyFunction();
};
```

- `React.lazy` splits at component level. The lazy component has to be rendered inside `Suspense`, which shows the fallback until the chunk has loaded. The imported module has to export the component as its default export, and `lazy()` has to be called at module top level, not inside a component.
- Lazy loading applies to client components. Server components are code split automatically. When a server component lazily imports a client component, automatic code splitting is not supported, so the file that calls `lazy()` has to be a client component for the split to happen.
- A client component loaded with `React.lazy` and `Suspense` is still prerendered on the server by default.
- `next/dynamic` is Next.js's wrapper around `React.lazy` and `Suspense`. Its `{ ssr: false }` option turns off server prerendering for that component. `ssr: false` works only when `dynamic()` is called in a client component; in a server component it raises an error ("`ssr: false` is not allowed with `next/dynamic` in Server Components").

```typescript
'use client';
import { lazy, Suspense } from 'react';

const HeavyComponent = lazy(() => import('@/components/HeavyComponent'));

export function Page() {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <HeavyComponent />
    </Suspense>
  );
}
```

## Route handlers and environment variables (carried over from `backend-patterns.md`)

- A route handler is a function exported from `route.ts` and named after the HTTP method. Supported names are `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD` and `OPTIONS`. It may be `async` or synchronous. It returns a `Response`.
- The first argument is the request. It is a `NextRequest` (from `next/server`), which extends the Web `Request`, so typing it as `Request` is valid. The second argument is a context object whose `params` is a Promise (see "Dynamic route parameters"). Both arguments are optional.
- `GET` route handlers are not cached by default from Next.js 15.0.0 onward (in 14 and earlier they were static by default). `fetch` requests are likewise not cached by default from 15.0.0 onward.

```typescript
export async function POST(req: Request) {
  const body = await req.json();
  return Response.json(created, { status: 201 });
}
```

- Environment variables prefixed `NEXT_PUBLIC_` are inlined into the JavaScript bundle at build time (`next build`): each literal reference `process.env.NEXT_PUBLIC_NAME` is replaced by the value present when the build ran. Changing the variable after the build has no effect until the next build.
- Only literal references are inlined. `process.env[name]` and `const env = process.env; env.NEXT_PUBLIC_NAME` are not.
- Anything without the prefix is available on the server only. In client code a reference to it is replaced with an empty string.
